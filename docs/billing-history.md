# Component billing history pages

`paginateSubscriptions` and `paginateCheckoutSessions` read the existing synchronized component tables. Each requires an original `userId` selected by a trusted host and accepts an optional exact `accountId`, typed `status`, and Convex `paginationOpts`. Selectors must be nonempty, trimmed original strings without control characters; they are rejected rather than normalized. There is no new lifetime or legacy-ID length cap. The account predicate is conjunctive with the buyer predicate. A user-only page includes valid legacy rows without an account ID; adding an account predicate intentionally excludes them.

Use independent cursors for the two readers. Page sizes are 1–100; they bound one page, never lifetime history. Optional caller read ceilings must be positive safe integers; stricter ceilings are preserved within the package policy of 200 rows/1 MB per invocation. Cursors bind the reader kind, buyer, optional account and status. Forward returned continuation and split cursors unchanged. Preserve `endCursor`, `pageStatus` and split obligations when a reactive pinned range grows. Cursor encoding is context binding, not authentication or a signed capability. Authorize every request and continued page before calling the package.

These are cached observations, not an atomic provider history certificate. Exhaustion means the selected component range was exhausted at that query, not that every provider event arrived. No reads synchronize or mutate provider resources. A completed Checkout session, an invoice, a trial and a paid one-time order are different facts; hosts must use their original request/fulfillment bindings and qualified payment evidence before making purchase or access decisions.

The SDK returns server-side component documents, including fields inappropriate for browsers. A host must whitelist its response: never forward Checkout `clientSecret`, `url` or arbitrary metadata. Do not infer buyer ownership from a caller-supplied account ID or remap historical buyers to a current account. Community, session and enabled-actor authorization remain app-owned. Missing or conflicting provenance is unavailable, not an empty successful financial history.

The matching Vite reference is `example/convex/billing/history/queries.ts`. Unlike the old synthetic-persona demo routes, this opt-in adapter requires a genuine Convex authenticated identity mapped uniquely through the existing `authTokenIdentifier` index, then an existing buyer/customer role. The ordinary demo does not configure authentication or mint that mapping; it therefore fails closed. A production host must supply its real account restriction and domain authorization checks rather than treating the example's demo role as a complete security model. The adapter takes no browser buyer/account selectors and whitelists safe observations.

Existing array readers retain their behavior. `listCheckoutSessionsByUser` remains a first-50 preview; it is not the pagination API. `getCheckoutSessionPageFromStripe` remains separate live provider discovery. Consumers can expose one authorized entrypoint returning both pages with independent cursors; these methods do not require a shared stream or a new ledger. In Dojo, DOJO-962 owns that authorized composition and DOJO-2238 owns the caller/UI migration; no UI or entitlement activation ships in this package slice.
